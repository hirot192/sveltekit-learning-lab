# 要件定義

## 1. 目的

SvelteKit を初めて学ぶ開発者が、動作するアプリとソースコードを往復しながら、次の問いに答えられるようになることを目的とする。

- URL にアクセスしたとき、どのファイルがどの順序で実行されるか
- サーバーで取得したデータが、どのように HTML と画面へ渡るか
- フォームの値が、どこで検証され、どのように DB へ保存されるか
- ログイン状態がリクエストをまたいで、どのように維持されるか
- 認証済みユーザーが他人のデータを操作できないよう、どこで認可するか
- 開発環境と Linux 上の本番環境で、何が異なるか

## 2. 想定読者

- HTML、CSS、JavaScript の基礎を理解している
- TypeScript、Svelte、SQL、Docker は未経験でもよい
- チュートリアルの写経から、実務的な構成へ進みたい

## 3. 題材

複数ユーザー対応の個人用ナレッジ管理アプリを作る。

各ユーザーはアカウントを作成し、自分のメモを登録、閲覧、編集、削除、検索できる。メモには複数のタグを付けられる。他ユーザーの非公開データにはアクセスできない。

## 4. 機能要件

### 4.1 教材機能

- **FR-L01:** 章ごとに学習目標、前提知識、操作手順を表示する
- **FR-L02:** デモ画面から、関係するリポジトリ内のファイルを確認できる
- **FR-L03:** 主要処理について、ブラウザから DB までの実行順を説明する
- **FR-L04:** SSR、クライアント遷移、Progressive Enhancement の差を確認できる
- **FR-L05:** 値の変更や意図的な失敗を試す「実験」項目を用意する
- **FR-L06:** 教材用の判断と、本番で追加すべき対策を区別して表示する

### 4.2 アカウントとセッション

- **FR-A01:** メールアドレス、表示名、パスワードで登録できる
- **FR-A02:** メールアドレスとパスワードでログインできる
- **FR-A03:** ログアウトすると現在のセッションを即時失効できる
- **FR-A04:** ユーザーは有効なセッション一覧を確認し、個別または一括で失効できる
- **FR-A05:** 保護ページへ未ログインでアクセスするとログイン画面へ誘導される
- **FR-A06:** ログイン後、許可された元の遷移先へ戻れる
- **FR-A07:** 期限切れ、削除済み、不正なセッション Cookie を安全に処理できる

### 4.3 メモとタグ

- **FR-N01:** ログインユーザーはメモを作成できる
- **FR-N02:** 自分のメモを一覧・詳細表示できる
- **FR-N03:** 自分のメモを編集・削除できる
- **FR-N04:** タイトルと本文をキーワード検索できる
- **FR-N05:** タグでメモを絞り込める
- **FR-N06:** 作成日時・更新日時で並び替えできる
- **FR-N07:** 一覧をページネーションできる
- **FR-N08:** すべての読み書きで所有者を検証し、他人のメモを露出しない

### 4.4 運用

- **FR-O01:** アプリと PostgreSQL を Docker Compose で起動できる
- **FR-O02:** DB マイグレーションを明示的なコマンドで実行できる
- **FR-O03:** 学習用の初期データを任意で投入できる
- **FR-O04:** アプリと DB のヘルスチェックを提供する
- **FR-O05:** Linux サーバー向けのデプロイ・更新・ロールバック手順を文書化する
- **FR-O06:** 秘密情報をリポジトリへ含めず、`.env.example` で必要項目を示す

## 5. 非機能要件

### 5.1 可読性

- SvelteKit の規約に沿い、独自の抽象化を増やしすぎない
- route、use case、repository の責務をファイル名から推測できるようにする
- コメントは構文の言い換えではなく、判断理由や境界条件を説明する
- 教材本文から対象ソースへ安定してリンクできる構造にする

### 5.2 セキュリティ

- パスワードは Argon2id などのパスワード用ハッシュで保存し、平文を保持しない
- セッショントークンは十分な乱数から生成し、DB にはトークンのハッシュを保存する
- Cookie は `HttpOnly`、`SameSite=Lax`、本番では `Secure` を設定する
- 認可は UI の表示制御ではなく、サーバー側の DB クエリ境界で強制する
- ログイン失敗時に、アカウントの存在を過度に漏らさない
- 入力値をサーバー側で検証する
- 秘密情報や内部エラーをレスポンスへ含めない
- リバースプロキシ由来ヘッダーは、信頼できる構成でのみ利用する

### 5.3 再現性と保守性

- Node.js、パッケージ、PostgreSQL、コンテナイメージのバージョンを固定する
- ロックファイルをコミットし、クリーン環境で同じ依存関係を取得できる
- x86_64 と ARM64 の一般的な Linux 環境を想定する
- lint、型検査、単体テスト、結合テスト、E2E テストを自動実行できる
- GitHub Actions でアプリとコンテナのビルドを検証する

### 5.4 ユーザビリティとアクセシビリティ

- 主要操作はキーボードで完結できる
- 入力欄にラベルを付け、エラーを対象フィールドと関連づける
- 色だけに依存して状態を伝えない
- 主要な作成・編集・削除フォームは JavaScript 無効時にも動作する

## 6. MVP の対象外

以下は発展課題とし、最初の完成条件には含めない。

- メールアドレスの所有確認
- パスワード再設定メール
- OAuth、パスキー、多要素認証
- 管理者画面とロールベースアクセス制御
- ファイルアップロード
- リアルタイム共同編集
- Kubernetes やクラウド固有サービスへのデプロイ

## 7. 受け入れ条件

- 新しい Linux 環境で README の手順だけを使い、アプリと DB を起動できる
- 登録、ログイン、ログアウト、セッション失効の E2E テストが通る
- メモの CRUD、検索、絞り込み、ページネーションの E2E テストが通る
- ユーザー A がユーザー B のメモを URL や直接 POST で取得・変更できない
- DB を削除した状態からマイグレーションと seed を再実行できる
- Cookie、セッション DB レコード、期限切れ時の挙動を教材上で説明できる
- 各章に、関連ファイルと確認用の実験が最低一つある
- CI 上で型検査、テスト、production build、Docker build が成功する
